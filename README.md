## Цель работы  

Освоить внедрение распределённого кэша в backend-приложение на Go с использованием Redis.  
Реализовать стратегию **cache-aside**, корректный **TTL** с **jitter**, **инвалидацию** кэша при изменении данных и **деградацию** сервиса при недоступности кэша.

## Реализованные механизмы  

### 1. Подключение Redis и проверка доступности  

```go
func NewRedisClient(cfg config.Config) *redis.Client {
    return redis.NewClient(&redis.Options{
        Addr:         cfg.RedisAddr,
        DialTimeout:  cfg.RedisDialTimeout,
        ReadTimeout:  cfg.RedisReadTimeout,
        WriteTimeout: cfg.RedisWriteTimeout,
    })
}
```

При старте выполняется Ping. Если Redis недоступен, выводится предупреждение, но сервер продолжает работу.

Базовый TTL — 120 секунд, jitter — до 30 секунд. Для списка значения уменьшены вдвое.

## Контрольные вопросы

**Что такое cache-aside?**

Cache‑aside — это подход, при котором приложение само решает, когда обращаться к кэшу, а когда — 
к основному хранилищу. Мы сначала проверяем, есть ли нужные данные в Redis, и если они там есть (cache hit), 
сразу возвращаем ответ, вообще не трогая базу данных. Если же в кэше пусто (cache miss), мы идём в основное хранилище, 
получаем данные, кладём их в Redis с определённым временем жизни и только после этого отвечаем клиенту. 
Приложение управляет кэшем вручную, а Redis не пытается самостоятельно что‑то догружать.

**Почему Redis не должен быть источником истины?**

Redis хранит данные в оперативной памяти и не гарантирует их сохранность при перезапуске или сбое. 
Кроме того, он не отвечает за бизнес‑логику и не знает, какие данные действительно актуальны. 
Единственным достоверным источником остаётся база данных или репозиторий. 
Если Redis вдруг потеряет часть информации или станет недоступным, 
мы не должны потерять данные, а просто временно перестаём получать ускорение. Так мы защищаем целостность системы.

Зачем нужен TTL?

TTL, или time‑to‑live, ограничивает срок жизни ключа в Redis. Без него данные могли бы копиться бесконечно, 
переполняя память и устаревая. Установив разумный TTL (например, 2–5 минут), 
мы заставляем кэш периодически «забывать» старые данные и при следующем запросе 
загружать свежие из основного хранилища. Это простой способ автоматического обновления кэша без сложных триггеров.

Что такое jitter?

Jitter — это случайная добавка к базовому TTL, которая немного разбрасывает время жизни ключей. 
Например, если базовый TTL равен 120 секундам, а jitter — 30 секунд, то реальный срок жизни ключа 
окажется где‑то от 120 до 150 секунд. Эта небольшая случайность не даёт массе ключей истечь одновременно, 
что снижает нагрузку на базу данных в момент их массового обновления.

Почему одинаковый TTL для всех ключей может быть проблемой?

Когда у всех записей одинаковый срок жизни, они истекают практически одновременно.
В этот момент десятки или сотни запросов могут одновременно пойти в базу данных за свежими 
данными, создавая резкий всплеск нагрузки. Jitter решает эту проблему,
распределяя истечение ключей во времени, и база данных получает запросы равномерно.

Как должен вести себя сервис при недоступности Redis?

Сервис должен продолжать работать, игнорируя ошибки Redis и направляя все запросы напрямую в основное хранилище. 
Он не должен падать, зависать или возвращать ошибки клиенту из‑за проблем с кэшем. В логах можно зафиксировать 
предупреждение, но пользователи этого не заметят — ответы будут приходить, просто чуть медленнее обычного. 
Это называется graceful degradation, или отказоустойчивость без потери функциональности.

Почему кэш нужно инвалидировать после изменения данных?

Если мы обновили или удалили задачу в базе данных, то старый кэш для этой задачи (и возможно, для списка задач) 
теперь содержит неверные, устаревшие данные. Если его не очистить, приложение будет показывать
пользователю неактуальную информацию, пока не истечёт TTL. Инвалидация — это принудительное удаление 
таких ключей сразу после изменения, чтобы следующий запрос гарантированно получил свежие данные.

Чем кэширование одной сущности проще, чем кэширование списка?

Отдельную задачу легко связать с конкретным ключом (tasks:task:15) и инвалидировать 
точечно при изменении именно этой задачи. Список же это коллекция,
которая зависит от множества сущностей. Если мы добавим, удалим или изменим любую задачу, весь кэшированный список
тут же устареет. Поэтому его приходится инвалидировать при любых модификациях, что делает кэш списка 
менее эффективным и более сложным в поддержке.

Почему Redis рассматривается как внешняя инфраструктурная зависимость?

Потому что Redis работает как отдельный сервер или кластер, доступный по сети, а не внутри процесса нашего приложения.
Он имеет собственный жизненный цикл, конфигурацию и может быть недоступен по многим причинам. 
Мы должны воспринимать его точно так же, как базу данных или брокера сообщений — как внешний компонент, 
отказ которого не должен ронять наш сервис.
